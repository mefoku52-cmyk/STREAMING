Evidence and diagnosis:
- /healthz previously always returned HTTP 200 and did not distinguish media/signaling readiness.
- The HTTP listener starts before asynchronous mediasoup/signaling initialization completes. The WebSocket upgrade handler is installed only during createSignaling.
- Before the upgrade handler exists, a premature GET/Upgrade request for /ws is handled as an ordinary HTTP request and the missing static route can return HTTP 404. This startup race was reproduced in backend/test/http-readiness.test.js: premature /ws handshake => 404 while /readyz => 503.
- This is a reproduced failure mode consistent with the reported symptom, not proof that it was the only cause of historical production/test failures; original exact URL/logs and deployed revision were unavailable.

Changes under verification:
- Added `ready` to /healthz and a separate /readyz endpoint: HTTP 503 until signaling exists and mediasoup worker reports alive; HTTP 200 only when ready === true.
- Updated integration test startup polling to require /readyz success and payload.ready === true.
- Added five authenticated /ws handshake + signaling-RPC probes per integration run after readiness.
